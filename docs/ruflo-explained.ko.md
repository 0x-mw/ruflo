# RuFlo 쉽게 이해하기: 계획하고, 기억하고, 테스트하고, 스스로 개선하는 AI 팀 만들기

*작성: rUv Cohen — Agentic Engineer / Founder @ Cognitum.One · 2026년 9월 7일*

> 원문은 [LinkedIn](https://www.linkedin.com/pulse/ruflo-explained-build-ai-team-plans-remembers-tests-improves-cohen-kdyxc)에 게시되었습니다.

대부분의 사람들은 채팅 창으로 AI를 처음 만납니다. 질문하고, 답을 받고, 다음에 할 일을 스스로 정합니다.

하지만 실제 업무는 답변 하나로 끝나는 경우가 드뭅니다. 기능 하나를 만들려면 조사, 코드, 테스트, 리뷰, 그리고 결정 사항의 기록이 필요합니다. 조사 프로젝트에는 출처와 비교가 필요하고, 결론이 근거에서 실제로 도출되는지 확인해 줄 사람도 필요합니다.

저는 이런 일을 체계적으로 정리하려고 RuFlo를 만들었습니다. 이 가이드는 기본 개념에서 시작해 첫 번째 쓸모 있는 작업까지 안내한 뒤, 메모리, 에이전트 팀, 플러그인, 평가가 어떻게 맞물리는지 보여 드립니다.

**읽는 순서 고르기:** 1~3장은 시스템을 설명합니다. 4~9장은 설정을 다룹니다. 10~14장은 실전 워크플로, 비용, 검증, 그리고 앞으로의 방향을 보여 드립니다. 모든 통합을 다 설치할 필요는 없습니다.

가장 간단하게 설명하면, RuFlo는 AI 어시스턴트가 다른 에이전트와 협업하고, 도구를 사용하고, 유용한 맥락을 기억하고, 결과를 확인하는 구조적인 방법을 제공합니다.

목표는 여전히 여러분이 정합니다. 추론은 여전히 여러분의 AI 모델이 합니다. RuFlo는 그 작업을 둘러싼 장치를 더 많이 제공할 뿐입니다.

이 글은 Claude, Codex, ChatGPT, Grok으로 시작하는 분들을 위한 실용적인 입문서입니다. 대규모 스웜이나 모든 플러그인이 필요하지는 않습니다. 쓸모 있는 작업 하나로 시작하고, 복잡도는 꼭 필요할 때만 더하세요.

## 1. 또 하나의 챗봇이 아니라 작업장으로 생각하세요

![AI 작업장](assets/ruflo-explained/ch01.jpg)
*계획이 조사, 구현, 테스트로 갈라졌다가 리뷰에서 다시 모입니다.*

모델은 문제를 곰곰이 생각하는 사람입니다. 스킬은 플레이북이고, 도구는 장비입니다. 메모리는 프로젝트 노트입니다. RuFlo는 이 작업장을 조율하도록 돕습니다.

이렇게 요청한다고 해 봅시다. *"이 애플리케이션을 리뷰하고 더 안전한 로그인 흐름을 제안해 주세요."*

한 에이전트는 현재 코드를 살펴봅니다. 다른 에이전트는 보안 문제를 찾습니다. 세 번째 에이전트는 테스트를 설계합니다. 이들의 결과는 하나의 권고안으로 모이고, 중요한 발견 사항은 다음 세션을 위해 남겨 둘 수 있습니다.

이것이 에이전트 스웜의 개념입니다. 하나의 목표를 공유하는 각자 한 가지 일에 집중하는 워커 여러 개를 뜻하며, 끝없이 대화만 나누는 봇 무리가 아닙니다.

Claude Code와 Codex에는 이미 강력한 네이티브 기능이 있습니다. RuFlo가 처음으로 이들을 유능하게 만드는 것은 아닙니다. 조율, 메모리, 워크플로, 통합이라는 또 하나의 계층을 더해 줄 뿐이며, 필요한 부분만 골라 쓰면 됩니다.

에이전트 팀은 작업을 나눌 수 있을 때 유용합니다. 작고 단순한 변경이라면 에이전트 하나가 더 나은 경우가 많습니다.

> **직접 해보기:** 프로젝트 맵, 테스트 계획, 보안 리뷰를 각각 별도의 결과물로 요청하세요. 서로 충돌하는 발견 사항은 코디네이터 하나가 정리하게 하세요. 두 줄짜리 수정이라면 에이전트 하나에게 맡기세요.

## 2. 헷갈리기 쉬운 네 가지 구성 요소

![모델, 스킬, MCP, 런타임](assets/ruflo-explained/ch02.jpg)
*헷갈리기 쉬운 네 가지 구성 요소를 순서대로 보여 줍니다.*

**모델:** Claude, GPT, Grok 또는 지원되는 다른 모델이 추론과 언어 생성을 담당합니다. RuFlo는 모델 가중치를 대체하는 것이 아닙니다.

**스킬:** 호환되는 에이전트에게 작업에 접근하는 방법을 가르치는 지침입니다. 스킬을 설치하면 어시스턴트가 플레이북을 갖게 됩니다. 그것만으로 서버가 시작되거나 파일 접근 권한이 주어지지는 않습니다.

**MCP:** Model Context Protocol은 어시스턴트가 도구를 찾아 호출하는 표준 방식입니다. RuFlo MCP 서버를 연결하면 호환되는 클라이언트가 상태 점검이나 프로젝트 메모리 검색 같은 동작을 요청할 수 있습니다.

**런타임과 플러그인:** 실제로 동작을 수행하는 소프트웨어입니다. 플러그인은 추가 기능을 묶어서 제공합니다. 일부는 스킬, 명령어, 또는 이벤트에 반응하는 훅도 포함합니다.

이 구성 요소들은 서로 맞물리지만 서로 바꿔 쓸 수는 없습니다. "스킬을 설치했다"와 "MCP 서버가 연결되었다"는 서로 다른 이야기입니다.

> **직접 해보기:** 어시스턴트에게 사용 중인 모델 이름, 설치된 RuFlo 스킬, 연결된 MCP 서버를 알려 달라고 하고, 해롭지 않은 도구를 하나 호출해 보게 하세요. "전부 설치되어 있습니다"라는 막연한 답보다 네 가지 명확한 답이 훨씬 유용합니다.

## 3. RuFlo로 할 수 있는 일

![메모리와 기능](assets/ruflo-explained/ch03.jpg)
*문서, 검색, 발견 사항이 공유 프로젝트 메모리로 모이는 모습.*

이 프로젝트가 다루는 기능 범위는 넓습니다. 내부 이름을 전부 익히지 않아도 되도록, 쓸모 있는 지도만 정리했습니다.

**작업을 계획하고 조율합니다.** 목표를 작업으로 나누고, 역할을 배정하고, 의존성을 추적하고, 결과를 합칩니다. 계층형 조율에서는 코디네이터 하나가 통합을 책임집니다. 작업 부하에 따라 어울리는 다른 조율 패턴도 있습니다. 동작하는 가장 단순한 구성을 고르세요.

**쓸모 있는 프로젝트 메모리를 유지합니다.** 결정, 발견 사항, 재사용할 수 있는 맥락을 저장합니다. AgentDB와 RuVector가 메모리와 검색 스택의 일부를 맡습니다. 검색은 정확히 일치하는 단어뿐 아니라 의미가 비슷한 내용도 찾아냅니다. 저장된 정보가 정확하고 범위가 적절하게 유지된다면, 같은 조사를 반복하는 일이 줄어드는 것이 이점입니다.

**이전 시도에서 배웁니다.** ReasoningBank, SONA 및 관련 구성 요소는 경험, 패턴, 피드백을 다룹니다. "효과가 있었던 일의 증거를 재사용한다"고 생각하세요. "기반 상용 모델이 스스로 재학습한다"는 뜻이 아닙니다. 학습 기능에도 평가와 합리적인 승격 규칙이 필요합니다.

**반복 가능한 워크플로를 만듭니다.** 계획, 구현, 테스트, 문서화, 리뷰를 한데 엮습니다. SPARC는 이 프로젝트가 제공하는 구조화된 개발 방식 중 하나입니다. 아키텍처 결정 기록은 어떤 선택을 한 이유를 남겨, 나중에 에이전트가 추측하지 않아도 되게 합니다.

**소프트웨어를 점검하고 테스트합니다.** 설정해 둔 범위에서 개발, 브라우저 자동화, 리뷰, 테스트 통합을 사용하세요. 실제 테스트 출력과 무엇을 확인했는지에 대한 설명을 요구하세요. 에이전트가 "완료했습니다"라고 말하는 것은 테스트 결과가 아닙니다.

**보안 점검을 추가합니다.** 보안 및 AIDefence 기능은 감사와 위협 감지를 뒷받침할 수 있습니다. 범위를 제한한 자격 증명, 격리된 환경, 승인 게이트를 보완하는 수단입니다. 어떤 플러그인도 임의의 도구 실행을 자동으로 안전하게 만들어 주지는 않습니다.

**비용과 진행 상황을 관찰합니다.** 상태 점검, 로그, 작업 상태, 비용 추적은 무엇이 실행되었고, 무엇이 실패했고, 무엇을 소비했는지 답하는 데 도움이 됩니다. 구성 요소 하나에 초록색 체크가 떴다고 해서 모든 통합이 동작한다는 증거가 되지는 않습니다.

**더 많은 환경을 연결합니다.** 프로바이더 통합, 로컬 모델 옵션, 페더레이션, 전문 플러그인이 시스템을 확장합니다. 일부 구성 요소는 가속을 위해 Rust나 WebAssembly를 사용합니다. 호환성, 하드웨어, 운영 요건은 기능마다 다릅니다.

**하네스(harness) 자체를 개선합니다.** MetaHarness 기능은 모델을 둘러싼 워크플로를 평가하고 다듬는 일을 지원합니다. 개선안은 기본값이 되기 전에 기준선과 비교해 테스트해야 합니다. 그럴듯하게 들리는 지시문이 반드시 더 잘 동작하는 지시문은 아닙니다.

IoT와 시장 데이터 도구를 비롯한 선택형 도메인 플러그인도 있습니다. 이들은 확장 기능이며 시작하기 위한 전제 조건이 아닙니다. 금융 통합에는 별도의 권한과 위험 통제가 필요합니다.

RuFlo README는 계속 갱신되는 기능 색인입니다. 기능 목록은 조사해 볼 지도로 보세요. 모든 기능이 여러분의 설치 환경에서 켜져 있다는 주장이 아닙니다.

### 실용적인 플러그인 지도

기반이 되는 `ruflo-core`부터 시작하세요. 조율된 팀에는 `ruflo-swarm`, 작업 계획에는 `ruflo-goals`, 반복 가능한 시퀀스에는 `ruflo-workflows`를 사용합니다. 오토파일럿과 루프 워커는 반복되거나 이어지는 작업을 위한 것이므로, 먼저 예산과 중지 조건을 정하세요.

지식 영역에서는 `ruflo-agentdb`, `ruflo-rag-memory`, `ruflo-rvf`, `ruflo-ruvector`, `ruflo-knowledge-graph`가 저장, 검색, 관계 파악이라는 서로 다른 필요를 각각 채웁니다. 쉽게 말해 데이터베이스는 노트를 보관하고, 검색은 쓸 만한 노트를 찾고, 그래프는 항목이 어떻게 이어지는지 기록합니다. 다섯 개를 모두 설치해야 하는 것은 아닙니다.

개발 영역에서는 코드 리뷰, 테스트, 브라우저 플러그인이 변경 사항을 살피고 동작을 확인하도록 돕습니다. ADR은 결정의 이유를 기록합니다. SPARC는 개발을 여러 단계로 구성합니다. DDD는 비즈니스 개념을 중심으로 소프트웨어를 구성하는 데 도움이 됩니다. 방법론이 존재한다는 이유만으로 도입하지 말고, 프로젝트를 더 이해하기 쉽게 만드는 방법을 고르세요.

보안 감사와 AIDefence는 점검을 더해 줄 뿐, 안전한 권한 설정을 대신하지 않습니다. 페더레이션은 서로 다른 머신에 설치된 에이전트를 연결하므로 네트워크 신뢰 경계가 생깁니다. 로컬 모델 라우팅은 추론이 실행되는 위치를 바꿀 수 있지만, 전체 워크플로가 비공개라고 말하기 전에 각 데이터 경로를 점검하세요.

MetaHarness는 에이전트를 둘러싼 설정, 즉 준비도, 설정상의 위험, 스냅샷, 회귀에 초점을 맞춥니다. 점수는 보증이 아니라 진단 신호로 다루세요. 저장소의 플러그인 카탈로그가 선택형 기능과 각 문서를 찾는 출발점입니다.

**예시: 고객 지원용 지식 어시스턴트.** 승인된 제품 문서를 제공하고, 질문마다 관련 구절을 검색하게 하며, 답변에 출처 인용을 요구합니다. 답하지 못한 질문은 기록합니다. 공유 메모리에 넣기 전에 추가 제안을 리뷰하세요. 모든 답이 자동으로 옳아서가 아니라, 지식과 점검이 나아지기 때문에 결과가 좋아집니다.

> **직접 해보기:** 짧은 아키텍처 결정을 출처, 날짜, 담당자와 함께 저장하세요. 새 세션에서 어시스턴트에게 그 결정을 조회하고 아직 유효한지 설명해 달라고 요청하세요. 저장되었다는 사실을 확인하는 것보다 올바르게 조회되는지가 더 중요합니다.

## 4. 가장 짧고 쓸모 있는 시작점: 스킬 설치

![플레이북 먼저 설치하기](assets/ruflo-explained/ch04.jpg)
*스킬, 프로젝트, 준비 완료. 이 순서대로.*

코딩 어시스턴트가 Skills 설치 프로그램을 지원한다면 터미널에서 다음을 실행하세요.

```bash
npx skills add ruvnet/ruflo --skill ruflo
```

프롬프트가 나오면 지원되는 에이전트와 설치 범위를 선택하세요. 컴퓨터의 모든 프로젝트를 한꺼번에 바꾸는 것보다 프로젝트 단위 설치가 파악하기 쉽습니다.

명령어는 `skills`이며 복수형입니다. 저장소 목록을 확인했더니 `ruflo`라는 이름의 스킬이 있었습니다.

이 명령은 호환되는 에이전트에게 RuFlo를 다루는 지침을 제공합니다. 모든 채팅 애플리케이션에서 통하는 범용 명령이 아닙니다. 호스팅되는 ChatGPT 대화에 이 명령을 붙여 넣는다고 해서 여러분 노트북의 `npx` 프로세스가 실행되지는 않습니다.

다음으로 어시스턴트에게 이렇게 요청하세요.

> RuFlo 스킬을 사용해 무엇이 설치되어 있고 무엇이 설치되지 않았는지 설명하세요. 아직 파일을 수정하거나 서비스를 연결하지 마세요. 이 프로젝트를 읽기 전용으로 리뷰하기 위한 최소 설정을 제안하세요.

**핵심 정리:** 먼저 어시스턴트가 스킬을 인식하는지 확인하세요. 그런 다음 첫 작업에 필요한 도구만 연결하세요.

> **성공 확인:** 어시스턴트가 프로젝트를 수정하지 않고 RuFlo 스킬과 그 한계를 설명할 수 있어야 합니다. 스킬을 찾지 못한다면 추가 패키지를 설치하기 전에 어떤 클라이언트와 설치 범위를 선택했는지 확인하세요.

## 5. Claude Code: 플러그인 또는 직접 MCP 연결 선택하기

![Claude Code 설정](assets/ruflo-explained/ch05.jpg)
*Claude Code로 들어가는 두 가지 경로: 플러그인 또는 직접 MCP 연결.*

패키지로 묶인 환경을 원하는 Claude Code 사용자라면, 다음은 일반 셸 명령어가 아니라 **Claude Code 안에서** 입력하는 명령어입니다.

```
/plugin marketplace add ruvnet/ruflo
/plugin install ruflo-core@ruflo
```

core부터 시작하세요. 구체적으로 필요해지면 조율 또는 메모리 플러그인을 추가합니다.

```
/plugin install ruflo-swarm@ruflo
/plugin install ruflo-rag-memory@ruflo
```

core 패키지는 MCP 통합을 제공합니다. 플러그인을 설치하는 것이 프로젝트의 모든 훅이나 백그라운드 서비스를 초기화하는 것과 같지는 않습니다.

MCP를 직접 등록하는 방식을 선호한다면 터미널에서 다음을 실행하세요.

```bash
claude mcp add ruflo -- npx --yes ruflo@3.38.23 mcp start
claude mcp list
```

연결 경로는 먼저 하나만 선택하세요. 같은 서버를 두 번 추가하면 도구 탐색이 헷갈릴 수 있습니다.

이 예시는 제가 확인한 npm 릴리스 `3.38.23`에 버전을 고정했습니다. 이후 릴리스에 따라 조용히 바뀌지 않도록 하기 위해서입니다. 이 패키지는 Node.js 20 이상을 요구합니다. 이 요구 사항을 충족하는, 현재 지원되는 Node 릴리스를 사용하세요.

클라이언트 권한과 문제 해결은 Anthropic의 MCP 설정 문서를 참고하세요.

> **성공 확인:** Claude Code가 의도한 RuFlo 서버를 하나만 나열하고 상태 점검을 실행할 수 있어야 합니다. lite 플러그인 경로는 전체 초기화 경로와 같은 훅 및 프로젝트 스캐폴드를 설치하지 않습니다. 더 큰 설정을 선택하기 전에 제안된 변경 사항을 먼저 확인하세요.

## 6. Codex: 같은 도구 서버 연결하기

![Codex 설정](assets/ruflo-explained/ch06.jpg)
*Codex를 같은 도구 서버에 연결한 다음, 결과를 직접 확인합니다.*

Codex CLI도 비슷한 로컬 MCP 등록을 지원합니다.

```bash
codex mcp add ruflo -- npx --yes ruflo@3.38.23 mcp start
codex mcp list
```

프로젝트의 Codex 초기화 경로를 사용할 수도 있습니다.

```bash
npx --yes ruflo@3.38.23 init --codex
```

초기화는 프로젝트 설정을 기록합니다. 특히 기존 저장소에서는 변경 사항을 리뷰하세요. 중요한 작업에 광범위한 설정을 적용하기 전에 버려도 되는 프로젝트에서 먼저 테스트하세요.

Codex에게 사용 가능한 RuFlo 도구를 나열하고, 상태 점검을 실행하고, 그 결과를 설명해 달라고 요청하세요. 설정 항목이 있다는 것만으로 프로세스가 정상적으로 연결되었다고 판단하지 마세요.

설정과 지원되는 전송 방식은 Codex MCP 문서에 나와 있습니다.

> **성공 확인:** Codex가 서버를 찾아내고, 읽기 전용 호출을 한 번 수행해 실제 결과를 반환할 수 있어야 합니다. 등록은 성공했는데 실행이 실패한다면, 모델을 탓하기 전에 실행 파일 경로, 작업 디렉터리, 필요한 환경 변수를 확인하세요.

## 7. Claude Desktop: 로컬 도구, 별도 설정

![데스크톱 설정](assets/ruflo-explained/ch07.jpg)
*Claude Desktop에는 자체 설정, 재시작, 도구 확인이 필요합니다.*

Claude Desktop의 로컬 MCP 설정은 Claude Code와 별개입니다. 문서에 안내된 로컬 서버 설정 방법을 사용하고, 다른 서버를 덮어쓰지 말고 기존 설정에 RuFlo 항목을 **병합**하세요.

```json
{
  "mcpServers": {
    "ruflo": {
      "command": "npx",
      "args": ["--yes", "ruflo@3.38.23", "mcp", "start"]
    }
  }
}
```

데스크톱 앱이 Node와 `npx`를 찾을 수 있어야 합니다. 설정한 뒤에는 클라이언트를 재시작하고 도구가 나타나는지 확인하세요. 터미널에서 명령이 동작한다고 해서 데스크톱 앱도 같은 실행 파일 검색 경로를 가진다는 보장은 없습니다.

> **성공 확인:** Claude Desktop을 재시작한 뒤, 연결된 RuFlo 도구를 알려 달라고 하고, 안전한 호출을 한 번 수행하도록 요청하세요. 설정할 때 흔히 겪는 문제는 데스크톱 애플리케이션의 실행 파일 검색 경로가 터미널과 다르다는 점입니다.

## 8. ChatGPT: 호스팅 연결은 다릅니다

![ChatGPT와 원격 접속](assets/ruflo-explained/ch08.jpg)
*호스팅 클라이언트에는 로컬 명령어가 아니라 인증된 원격 엔드포인트가 필요합니다.*

웹의 ChatGPT에는 로컬 stdio 명령어가 아니라 접근 가능한 **원격** MCP 엔드포인트가 필요합니다. 현재 개발자 모드 문서에는 워크스페이스 제어 정책에 따라 자격을 갖춘 유료 요금제에서 지원한다고 나와 있습니다.

설정(Settings) → 보안 및 로그인(Security and login)에서 개발자 모드를 켜세요. 플러그인(Plugins)에서 관리자가 제공한 인증된 원격 MCP URL로 개발자 모드 앱을 만든 다음, 허용된 도구를 선택하세요.

RuFlo 배포 환경은 그 원격 엔드포인트나 적절한 게이트웨이를 직접 제공해야 합니다. 이 가이드는 프로젝트 웹사이트가 MCP 엔드포인트라고 가정하지 않습니다. 인증, 도구 제한, 운영 책임자가 없는 상태에서 로컬 명령어 서버를 인터넷에 노출하지 마세요.

읽기 전용 도구를 최소한으로 구성해 시작하세요. 메뉴 이름과 제공 여부는 바뀔 수 있으니 ChatGPT 개발자 모드 공식 안내를 따르세요.

> **성공 확인:** 서버 운영자에게 정확한 서버 URL을 확인하고, 인증한 뒤, 의도한 도구를 찾아내는지 확인하고, 허용된 읽기 동작을 한 번 실행하세요. 권한이 없는 동작은 거부되는지도 테스트하세요. 파일을 읽거나 명령어를 실행할 수 있는 서버에는 인증 없는 공개 터널을 쓰지 마세요.

## 9. Grok, Grok Bot, Grok Build는 서로 다른 환경입니다

![Grok 환경](assets/ruflo-explained/ch09.jpg)
*CLI, 웹, 봇은 권한이 서로 다른 세 가지 환경입니다.*

Grok Build CLI는 로컬 MCP 연결을 문서화하고 있습니다. 문서에 나온 명령어 패턴을 RuFlo에 쓸 수 있습니다.

```bash
grok mcp add ruflo -- npx --yes ruflo@3.38.23 mcp start
grok mcp list
grok mcp doctor ruflo
```

이것은 Grok Build MCP 문서를 바탕으로 한 설정 예시일 뿐, 제가 여러분의 Grok 설치 환경에서 테스트했다는 뜻이 아닙니다. Grok Build는 스킬과 플러그인도 지원하지만, 에이전트 번들 전체를 가져오기 전에 호환성을 먼저 확인하세요.

웹의 Grok은 원격 서버 URL과 인증을 사용하는 커스텀 커넥터를 문서화하고 있습니다. ChatGPT와 마찬가지로, 공개 웹사이트 URL과 보안이 적용된 MCP 엔드포인트는 같은 것이 아닙니다.

Grok Bot은 자체 관리형 환경과 사용 가능한 통합을 갖고 있으며, 계정별 기능도 다를 수 있습니다. Grok Bot 문서를 참고하고, 먼저 실제로 어떤 터미널, 스킬, 커넥터 옵션을 쓸 수 있는지 알려 달라고 요청하며 시작하세요.

> 이 환경이 로컬 RuFlo MCP 프로세스를 지원하는지, 아니면 인증된 원격 커넥터를 지원하는지 확인하세요. 아무것도 설치하기 전에 사용 가능한 경로와 권한을 보고하세요. 제 노트북에 접근할 수 있다고 가정하지 마세요.

네 가지 생태계를 관통하는 교훈은 간단합니다. **스킬은 워크플로를 가르치고, MCP는 도구를 연결하며, 그 도구를 어디서 실행할 수 있는지는 호스트가 결정합니다.**

> **성공 확인:** Grok에게 지금 CLI, 브라우저, 관리형 봇 중 어떤 환경에서 실행 중인지 확인하게 한 다음, 사용 가능한 연결 방법을 설명하게 하세요. CLI 명령어가 통한다고 해서 웹 계정에도 같은 통합이 있다고 여기지 마세요.

## 10. 첫 번째 실전 작업: 범위가 정해진 프로젝트 리뷰

![첫 번째 전체 워크플로](assets/ruflo-explained/ch10.jpg)
*제안하고, 테스트하고, 승인하고, 릴리스한 다음 다시 반복합니다.*

비밀 정보가 없는 작은 프로젝트를 사용하세요. 배포가 아니라 점검부터 시작하세요.

> 필요한 부분에는 RuFlo를 활용해 이 프로젝트를 리뷰하세요. 먼저 프로젝트의 목적과 테스트 실행 방법을 요약하세요. 독립적인 리뷰 작업 세 가지를 제안하세요. 첫 번째 패스는 읽기 전용으로 유지하세요. 의존성을 설치하거나, 소스 코드를 추가 서비스로 보내거나, 파일을 수정하거나, 게시하거나, 배포하지 마세요. 파일 참조, 불확실한 부분, 실제로 실행한 정확한 점검 내용과 함께 발견 사항을 반환하세요.

계획을 리뷰한 뒤에는 특정 변경 하나만 승인하세요. 에이전트에게 명확한 인수 테스트와 중지 조건을 주세요.

> 합의한 입력 유효성 검사 변경만 구현하세요. 관련 없는 작업은 그대로 두세요. 관련 테스트를 실행하세요. diff, 테스트 결과, 남은 위험 요소를 보여 주세요. 커밋이나 배포 전에 멈추세요.

목표, 계획, 범위가 정해진 실행, 증거, 리뷰로 이어지는 쓸모 있는 엔드 투 엔드 워크플로입니다. 에이전트 수십 개를 한꺼번에 켜는 것보다 디버깅하기도 쉽습니다.

> **직접 해보기:** 비밀 정보가 없는 작은 저장소를 사용하세요. 기준선 테스트 결과를 저장하고, 입력 유효성 검사 수정 하나를 승인한 뒤, 같은 테스트를 다시 실행해 비교하세요. 결과물은 "완료했습니다"라는 메시지가 아니라 변경 사항과 증거입니다.

## 11. RuFlo가 진가를 발휘하는 곳

![실무 활용 사례](assets/ruflo-explained/ch11.jpg)
*하나의 core로 소프트웨어, 조사, 운영, 미디어를 아우릅니다.*

**소프트웨어 출시:** 구현, 테스트, 리뷰를 분리해 같은 에이전트가 자기 작업의 유일한 심사자가 되지 않도록 합니다.

**낯선 저장소 파악:** 아키텍처를 파악하고, 진입점을 찾고, 가정을 문서화하고, 발견 사항을 다음 작업에서도 쓸 수 있게 남겨 둡니다.

**조사와 분석:** 출처 수집, 비교, 검증을 나눠 맡깁니다. 출처 인용은 결론과 함께 저장하세요. 도구에 접근할 수 있다고 해서 근거 없는 주장이 사실이 되지는 않습니다.

**운영 런북:** 반복되는 점검을 담당자, 로그, 명확한 에스컬레이션 규칙이 있는 워크플로로 바꿉니다. 복구 조치를 허용하기 전에 진단부터 시작하세요.

**콘텐츠와 미디어 제작:** 승인된 통합을 통해 조사, 초안 작성, 에셋 생성, 리뷰를 조율합니다. 모델이 게시물이나 영상을 제안할 수는 있지만, 게시와 유료 생성에는 여러분이 정한 권한과 예산이 여전히 필요합니다.

**장기 프로젝트:** 결정 사항과 평가를 거친 패턴을 보관해, 새 세션이 과거를 재구성하는 데 시간을 덜 쓰게 합니다.

> **직접 해보기:** 매주 이미 하고 있는 반복 작업 하나를 고르세요. 입력, 기대 출력, 지출 한도, 리뷰어를 적어 보세요. 그 워크플로부터 구축하세요. 미디어 예시라면 게시 전에 대본, 시각 자료 계획, 에셋 영수증, 오디오 점검, 최종 리뷰를 필수로 요구하세요.

## 12. 비용: 에이전트가 많다고 저절로 싸지지는 않습니다

![유용한 결과로 측정하기](assets/ruflo-explained/ch12.jpg)
*시간과 비용은 전달된 가치와 견줄 때만 의미가 있습니다.*

절감 효과는 반복 작업을 피하고, 알맞은 맥락를 조회하고, 작업마다 적절한 모델을 쓰고, 실수를 더 일찍 잡아내는 데서 나옵니다.

병렬 작업은 대기 시간을 줄여 주지만 토큰 사용량은 늘릴 수 있습니다. 간단한 예를 들어 보겠습니다. 서로 독립적인 작업 3개가 각각 10분씩 걸린다고 합시다. 순차로 처리하면 30분입니다. 함께 실행하면 10분에 통합 5분을 더해 총 15분 정도가 걸릴 수 있습니다. 그렇다고 모델 비용이 절반이 되는 것은 아닙니다. 통합 과정과 중복된 맥락 때문에 오히려 늘어날 수 있습니다.

이는 예시일 뿐 RuFlo 벤치마크가 아닙니다. 의존성, 프로바이더 한도, 재시도에 따라 결과가 달라집니다.

**승인된 결과 1건당 비용**을 측정하세요. 모델 사용량, 도구 요금, 인프라, 재시도, 사람의 리뷰 시간이 모두 포함됩니다. 더 싸게 실행했더라도 쓸 수 없는 결과물이 나왔다면 절감이 아닙니다.

제가 쓰는 기본 규칙은 이렇습니다. 코디네이터 하나, 정말로 독립적인 작업 몇 개, 고정된 예산, 분명한 종료 기준.

> **직접 해보기:** 같은 작은 작업을 에이전트 1개로 한 번, 작은 팀으로 한 번 실행해 보세요. 소요 시간, 총 요금, 재시도 횟수, 리뷰어가 쓴 시간, 인수 테스트 통과 여부를 기록하세요. 적절한 비용으로 더 나은 승인된 결과를 내는 쪽을 택하면 됩니다.

## 13. 제가 검증한 것, 그리고 직접 검증해야 할 것

![연결하고, 테스트하고, 증명하기](assets/ruflo-explained/ch13.jpg)
*연결은 증명이 아닙니다. 실행과 증거가 증명입니다.*

처음 글을 쓸 때의 검증에서는 npm 릴리스 `3.38.23`, 공개된 스킬 목록, 초기화 도움말, MCP 도구 탐색을 확인했습니다. CLI는 도구 333개를 보고했습니다. 이 숫자는 사용 가능한 인터페이스를 나타낼 뿐, 여러분의 환경에서 333가지 기능이 증명되었다는 뜻이 아닙니다.

```bash
npx --yes ruflo@3.38.23 --version
npx --yes ruflo@3.38.23 doctor
npx --yes ruflo@3.38.23 mcp tools
npx --yes ruflo@3.38.23 mcp exec --tool system_health
```

설정된 연결은 메모리, 설정, MCP 프로세스 점검을 통과했습니다. 초기화되지 않은 임시 디렉터리에서 같은 상태 점검 명령을 실행하자 설정과 메모리가 없다고 올바르게 보고했습니다. 일부 고급 서브시스템 점검은 `healthy`가 아니라 `unknown`으로 보고되었습니다. 환경에 따라 결과가 달라집니다.

이 릴리스에서 `doctor --fix`는 제안 명령을 출력할 뿐이므로, 모든 것을 자동으로 고쳐 준다고 설명해서는 안 됩니다.

워크플로를 신뢰하기 전에 도구 탐색, 권한, 실제 실행, 출력을 검증하세요. 등록된 에이전트나 작업 기록은 그 작업이 실행되었다는 증거가 아닙니다.

> **성공 확인:** 도구 이름, 입력 범위, 결과, 타임스탬프, 비용, 테스트 증거를 담은 작은 영수증을 저장하세요. 새 세션에서 같은 과정을 반복하세요. 결과를 재현하지 못한다면 자율성을 더 부여하기 전에 원인부터 조사하세요.

## 14. 여러 머신에 걸친 작업: 오픈 스웜 페더레이션

위에서 설명한 내용은 모두 머신 한 대에서 실행됩니다. 페더레이션을 쓰면 *서로 다른* 머신, 즉 노트북, Windows PC, Linux 서버, 클라우드 데스크톱, 또는 전혀 다른 사람의 환경에 있는 에이전트끼리 서로를 확인하고, 상태를 공유하고, 작업을 인계하고, 누가 무엇을 맡을지 합의할 수 있습니다. 모든 메시지는 보낸 사람이 암호학적으로 서명하므로 누가 무슨 말을 했는지 항상 알 수 있습니다.

페더레이션 방식은 두 가지이며, 하나만 써도 되고 둘 다 써도 됩니다.

- **프라이빗 메시 (agentbbs).** 직접 관리하는 머신끼리 서로의 키를 고정(pin)하고 일반 HTTP로 서로의 룸을 가져옵니다. LAN, VPN, Tailscale에서 동작하며 특별한 네트워크가 필요 없습니다. 여러분의 머신 플릿에 적합합니다.
- **x.ruv.io의 오픈 스웜.** `https://x.ruv.io` 뒤에 있는, 멤버십으로 접근을 제한한 공유 Nostr 릴레이입니다. 초대를 받은 사람은 누구나 *자기 자신으로* 참여할 수 있습니다. 초대는 본인 머신에만 있는 키로 사용하므로 관리자가 누구의 신원도 보관하지 않습니다. 여러분이 관리하지 않는 사람 및 에이전트와 협업할 때 적합합니다.

**오픈 스웜 참여는 명령어 하나면 됩니다 (RuFlo 3.41.0 이상):**

```bash
npx ruflo federation join --code v2.…      # 비공개로 받은 초대 코드
npx ruflo federation roster                # 지금 온라인인 사람
npx ruflo federation sync                  # 스웜에 올라온 게시물
npx ruflo federation claims                # 누가 어떤 작업을 맡았는지
```

첫 번째 명령은 `~/.ruflo/nostr.key`에 키를 생성하고(본인만 읽을 수 있음), 릴레이에 직접 초대 코드를 제출해 사용하고 멤버십을 확인합니다. 그 이후로는 본인 신원(키)으로 게시합니다.

**클레임(claim)은 에이전트끼리 충돌하는 일을 막아 줍니다.** 에이전트는 공유 작업을 시작하기 전에 리소스에 클레임을 게시합니다. 리소스당 소유자는 한 명이며, 먼저 올린 유효한 클레임이 우선하고, 소유자만 해제하거나 인계할 수 있습니다. 시작하기 전에 `federation claims`를 확인하면 다른 사람이 하던 일을 중복해서 하지 않게 됩니다.

**Seraphina는 스웜의 코디네이터입니다.** 목표를 주면 실시간 명단, 클레임 보드, 최근 메시지를 읽고, 쉬운 말로 된 안내와 구체적인 제안을 돌려줍니다. 어떤 노드가 무엇을 맡아야 하는지, 무엇이 잘못될 수 있는지가 담겨 있습니다. Seraphina는 질문을 처리할 수 있는 가장 저렴한 모델 티어를 골라 주는 cognitum meta-llm 게이트웨이를 통해 추론합니다. Seraphina의 제안은 명령이 아니라 조언입니다. 운영자가 수락한 제안만 직접 게시합니다. `x.ruv.io/mcp`의 `seraphina_guidance` 도구로, 그리고 RuFlo 안에서 사용할 수 있습니다.

**보안, 한 문단으로.** 서명된 메시지로 작성자를 검증할 수 있습니다. 멤버십은 초대로 제한되고 모든 연결은 인증됩니다(NIP-42). 게이트웨이가 *자신의* 신원으로 수행하는 모든 작업, 즉 초대 발급, 멤버 가입 허용, 브로드캐스트에는 관리자 토큰이 필요하고 요청 횟수도 제한됩니다. 일반 사용자는 그 경로를 건드릴 일이 없습니다. 메시지 내용은 에이전트에 대한 지시가 아니라 항상 데이터로 취급합니다. 그리고 기억해야 할 규칙은 하나입니다. **페더레이션 메시지에는 절대 비밀 정보를 넣지 마세요.**

**페더레이션 인수 테스트:** 초대로 참여하고, 명단에서 자신을 확인하고, 리소스 하나를 클레임한 뒤, 두 번째 머신에서 여러분의 클레임이 보이는지 확인하세요. 이 왕복이 동작하면 나머지도 믿어도 됩니다.

## 15. 앞으로의 방향: 일을 이어서 끌고 가는 어시스턴트

![유용한 자율성](assets/ruflo-explained/ch14.jpg)
*계획, 실행, 확인, 학습의 중심에는 항상 여러분이 있습니다.*

흥미로운 변화는 AI에게 답을 묻는 데서 범위가 정해진 책임을 맡기는 쪽으로 옮겨 가고 있다는 점입니다.

계획을 세우고, 도구를 쓰고, 쓸모 있는 메모리를 유지하고, 자신의 시도를 평가할 수 있는 어시스턴트는 대화와 대화 사이에서도 프로젝트를 더 많이 이어 갈 수 있습니다. 하지만 자율성은 결과를 이해하고 통제할 수 있을 때만 도움이 됩니다.

저는 시스템이 효과가 있었던 것은 기억하되 어제의 실수는 남기지 않기를 바랍니다. 혼란을 키우지 않고 위임하고, 권한을 슬며시 넓히지 않으면서 더 빠르게 움직이기를 바랍니다.

RuFlo는 이런 접근을 위한 구성 요소를 제공합니다. 전부 쓸 필요는 없습니다. 작게 시작하고, 결과를 측정하고, 분명히 짚을 수 있는 문제를 해결하기 위해서만 다음 기능을 추가하세요.

**첫 번째 인수 테스트:** 어시스턴트가 의도한 도구를 찾아내고, 범위가 정해진 작업 하나를 끝내고, 증거를 보여 주고, 권한 경계에서 멈출 수 있습니까? 그렇다면 쓸 만한 토대가 마련된 것입니다. 거기서부터 확장하세요.

[저장소와 README](https://github.com/ruvnet/ruflo), [사용자 가이드](USERGUIDE.md), 그리고 RuFlo 웹 인터페이스를 살펴보세요. 일부 문서는 서로 다른 릴리스 시점을 기준으로 하므로, 명령어가 다르면 설치된 CLI의 도움말을 확인하세요.

> **다음 단계:** 프로젝트 하나, 연결 경로 하나, 인수 테스트 하나를 고르세요. 메모리, 두 번째 에이전트, 반복 가능한 워크플로는 그것이 분명히 짚을 수 있는 문제일 때만 추가하세요. 유용한 자율성이란 여러분이 이해하는 경계 안에서 측정 가능하게 나아가는 것입니다.

*설치 예시는 RuFlo 3.38.23에 고정되어 있으며, 페더레이션 장은 3.40.0(메시, x.ruv.io, Seraphina)과 3.41.0(`federation join`)을 기준으로 합니다. 클라이언트 기능과 릴리스 세부 사항은 바뀔 수 있습니다. 사실적인 AI 생성 일러스트와 합성 내레이션은 Cognitum Media와 fal로 이 가이드를 위해 제작했습니다. 개념을 보여 주는 자료이며 실제 에이전트 실행 화면이 아닙니다.*
